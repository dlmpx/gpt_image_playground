# 项目宪章

## 项目身份

当前代码仓库基于开源项目 [`CookSleep/gpt_image_playground`](https://github.com/CookSleep/gpt_image_playground) 进行二次开发，**不是原始首发项目**。

我们会持续保留上游项目的许可证、署名与归属说明，并在此基础上做定向演进，而不是模糊上游来源或假装从零原创整套代码。

## 一句话主旨

基于上游 `gpt_image_playground` 的开源基础，做一个**本地优先、图像优先、面向个人创作者**的创作工作台，并重点服务“**四视图角色设计抽卡工作流**”。

## 核心用户

核心用户不是大众站点访客，而是高频迭代型个人创作者：

- 会反复生成、筛选、回溯，而不是一次性出图
- 会使用参考图、遮罩和局部修正，而不是只写一段提示词
- 需要显式保留版本链、候选分支和阶段推进关系
- 更在意创作工作流是否顺手，而不是平台是否花哨

## 产品定义

当前项目不是：

- 通用 AI 内容商业站克隆
- 大而全的模型广场
- 以社区、账号、协作为优先的 SaaS 平台
- 以节点编排平台为当前主线的系统

当前项目是：

- 一个本地优先的个人图像创作工作台
- 一个建立在上游优秀基础上的定向二开项目
- 一个围绕角色设计抽卡与多阶段演化流程的工具
- 一个强调人工审美判断、可回溯、可复用的工作流产品

## 核心原则

- **上游归属清晰**：始终明确基于 `CookSleep/gpt_image_playground` 二次开发
- **本地优先**：创作资产、历史记录、阶段状态默认服务本地工作流
- **图像优先**：近期主轴是图像工作流，不把项目立即扩成视频平台
- **工作流优先**：任何功能都要缩短或强化实际创作闭环
- **版本优先**：结果不是终点，阶段、候选、回溯和分叉关系才是资产
- **少而强**：优先做一条顺畅主路径，而不是堆砌能力目录

## 当前主链路

目标链路：

1. 准备提示词、参考图和阶段目标
2. 生成一批候选结果
3. 对候选做筛选、标记、晋级或淘汰
4. 将结果带入下一阶段继续生成
5. 必要时做局部遮罩编辑和修正
6. 保留多分支推进、回溯与对比关系
7. 导出结果与元数据，形成可复用资产

## 特定领域方向

本项目将现有通用 playground 收敛到更具体的角色设计场景：

- 多文化幻想抽卡
- 阶段推进式角色探索
- 四视图与设定演化
- 候选并行推进与分支回看
- 风格冲突、特征漂移、垫图污染等风险管理

## 不做清单

以下方向默认不进入当前主线：

- 社区广场、点赞、关注、内容分发
- 账号体系与团队协作
- 为了“支持更多 provider”而支持更多 provider
- 不做视频功能（已封存）
- 以节点编排替代当前产品主路径

## 命名与叙事规则

为避免产品能力名和 API 模型名混淆：

- 产品层可使用 `ChatGPT Images 2.0` 等能力表述
- 配置层与适配层保留实际 provider model id

这样可以在接口模型名变化时，保持产品叙事稳定。

## 近期里程碑

### 里程碑 1：图像工作台定型

- 明确二开身份与上游归属
- 建立项目 / 阶段 / 候选 / 分支的基础语义
- 把当前任务列表推进为“可回溯工作流”
- 保持现有生成、参考图、遮罩、本地历史能力的可复用性

### 里程碑 2：角色设计工作流增强

- 增加阶段推进入口
- 增加候选晋级 / 淘汰 / 主推等轻量状态
- 增加文化调频、阶段说明、风险提示等工作流辅助信息
- 提升版本复用与筛选效率
- 后续版本将围绕用户自定义模板和并行工作区展开

## 需求裁剪规则

后续需求进入开发前，先问四个问题：

1. 它是否服务个人创作者，而不是泛平台用户？
2. 它是否强化了角色设计工作流，而不是单纯加功能？
3. 它是否提升了回溯、分支、复用或资产组织能力？
4. 它是否让项目更聚焦，而不是更发散？

如果一个需求有两项以上回答是否定的，应降级、延后或拒绝。
